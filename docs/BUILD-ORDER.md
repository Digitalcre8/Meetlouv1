# Build order: the capture spine

Each milestone ends at its "done" and stops for review. Every verification below runs with **no real credentials**: the local Supabase stack (`supabase start`, Docker) generates throwaway keys, vendors are replaced by fixtures and fakes, and time and ids are injected.

Cross-cutting rule: a milestone is not done until its non-negotiable tests exist and fail when the guarantee is broken (prove it once by temporarily breaking the guarantee).

## M0. Scaffold and CI (this commit)

- **Done when:** `pnpm install --frozen-lockfile && pnpm verify` passes from a clean checkout; CI runs the same steps; the guards script rejects (a) a reference to the service role in `apps/web`, (b) a gap or misnumbering in migrations, (c) an edit to an existing migration.
- **Verified by:** CI green on the scaffold; deliberately editing a throwaway migration on a branch turns the guard red.
- **Not included:** any application code, `supabase/config.toml` (generated by `supabase init` in M1, which needs the CLI), the Supabase project itself.

## M1. Schema, tenancy, RLS, audit

Migrations `0001…`: `firms`, `firm_members`, `matters`, `participants`, `firm_phone_numbers`, `inbound_email_keys`, `retention_policies`, `audit_log` (hash chained), helper `auth_firm_ids()`, roles and grants. Add the local-stack job to CI.

- **Done when:** the cross-tenant test passes for every tenant table (user of firm A reads and writes nothing of firm B); a meta-test fails if any public table lacks RLS + FORCE RLS or has zero policies; reference-table changes write audit rows; the audit hash chain verifies and a tampered row is detected.
- **Verified by:** SQL/Vitest tests against the local stack, seeded with synthetic firms and users.
- **Also resolves:** member roles and how the first firm and `colp` are provisioned (operator script, not UI).

## M2. Evidence tables, events, receipts, approvals

`calls`, `call_recordings`, `transcripts`, `generated_outputs`, `approvals`, `emails`, `email_attachments`, `matter_assignments`, `events`, `event_reads`, `webhook_receipts`, `quarantined_inputs`, the append-only triggers, views `matter_timeline`, `email_threads`, `client_visible_outputs`.

- **Done when:** UPDATE and DELETE raise for `service_role`, `authenticated` and the table owner's application connections on every evidence table, with one parameterised test that iterates the list of evidence tables (so a new one cannot be forgotten); `calls` rejects `given` without `consent_given_at`; a recording insert is rejected for a non-consented call; `approvals` rejects a non-fee-earner and rejects service-role inserts; `client_visible_outputs` returns nothing for an unapproved output and returns it after approval; duplicate inserts on every idempotency key are no-ops.
- **Verified by:** local-stack tests, including the failure cases above.

## M3. Twilio inbound voice: consent and call row (built)

`supabase/functions/twilio-voice` (Deno entrypoint) over `packages/capture`. Built as **two steps that Twilio drives**, because the call row is the consent record and must not claim consent before the announcement has played:

1. `POST <base>`: verify signature, route on `matters.line_e164`, return the announcement (`<Say>` naming the firm and property) then `<Redirect>` to `<base>/announced?started=<epoch>`. **Nothing is written** (an unrouted number writes an audit row and is answered politely).
2. `POST <base>/announced?started=...`: Twilio only calls this once the announcement has finished and the caller is still on the line. Now the `calls` row is inserted (`ON CONFLICT (call_sid) DO NOTHING`) with `consent_given_at` = this moment, and the TwiML is `<Dial record="record-from-answer-dual" recordingStatusCallback=...>` to the responsible fee earner.

Consent is the announcement itself (no keypress); the wording is a constant in `consent.ts`, pinned by a test so no change can pass unnoticed. This answers open question 2 as "implied by staying on the line". `/recording-status` answers 501 until M4.

- **Done when (all met):** a valid signature is accepted; a tampered, unsigned, or host-signed request returns 403 and writes nothing; the same CallSid delivered three times gives one row and identical answers; an unknown number is answered politely, writes one audit row (idempotent) and creates no matter or call; no response carries a recording instruction unless a consented call row exists (property test, plus a mutation check that it fails if the row is written early).
- **Verified by:** unit tests with an in-memory store (`packages/capture`), and `supabase/tests/voice.test.ts`, which serves the real entrypoint under Deno (`pnpm functions:serve`) and replays `fixtures/` at it against the local database.
- **Not verified here:** the Supabase Edge Runtime itself (the sandbox cannot pull its image). The entrypoint is plain `Deno.serve` with a per-function `deno.json` import map, `verify_jwt = false`, and passes `deno check`; confirm with `supabase functions serve` before first deploy.

## M4. Recording ingest and the dual-channel check

Recording-status callback, download with `RequestedChannels=2`, WAV header parser, hash, Storage write, `call_recordings` row, `call.recording_stored` or `call.recording_mono` event.

- **Done when:** a stereo fixture is stored with `channels = 2`; a mono fixture (Twilio ignoring the request) is stored with `channels = 1`, raises `call.recording_mono`, and `diarised` can never be set true for it (DB check, tested); a truncated or non-WAV payload is quarantined, not stored under the matter; a callback for a non-consented call is quarantined; duplicate callbacks create one row and one object; bad signature rejected.
- **Verified by:** synthetic WAVs generated in the test (header-accurate, a few KB), and a fake Twilio media server inside the harness that can be told to return stereo, mono, truncated, or 404-then-200.

## M5. Email ingest (SendGrid Inbound Parse)

Edge Function `sendgrid-inbound` at `/sendgrid-inbound/{public_id}/{secret}`. zod parsing of the multipart form, raw MIME and attachments to Storage, `emails`, `email_attachments`, events, auto-assignment by participant address or matter reference, otherwise unassigned.

- **Done when:** wrong or revoked secret rejected in constant time (test uses a timing-safe-compare spy and a wrong-length secret); the same Message-ID delivered ×3 yields one row; a reply that arrives **before** its parent, a reply with only In-Reply-To, a reply with References but a changed subject, and two unrelated threads with the identical subject all thread correctly in `email_threads`; attachments are stored once per hash and `sniffed_content_type` is recorded; oversize payload rejected with a recorded outcome; a missing Message-ID is synthesised and flagged; no log line contains body, address or filename (test captures logger output).
- **Verified by:** multipart fixtures in `fixtures/sendgrid/`, replayed by the harness.

## M6. Transcription and summarisation

`Transcriber` and `Summariser` interfaces in `packages/providers` with a deterministic fake and one adapter stub per chosen vendor (adapter is configuration, not a milestone dependency). Job runner triggered by `call.recording_stored` and `email.received`.

- **Done when:** the fake produces stable output; swapping providers requires no change outside `packages/providers` and configuration (compile-time test against the interface); `diarised` is true only for dual-channel input; a model output is stored with provider, model, prompt version and hash; outputs default `client_visible = false`; `client_visible_outputs` serves nothing until a fee earner approval exists; a provider failure records an event and retries idempotently; model output is zod-validated and treated as untrusted text.
- **Verified by:** unit tests with the fake; local-stack test of the approval gate.

## M7. Retention, legal hold, erasure

`legal_holds`/`legal_hold_releases`, `erasure_schedule`, retention runner as a scheduled Edge Function (pg_cron), `retention_runner` role.

- **Done when, with an injected clock:** a matter closed with an N-year policy is scheduled for `closed_at + N`; a matter is not erased the day before and is erased the day of; a matter on hold is never erased and a hold placed **after** scheduling but before the run blocks it; releasing a hold lets the next run erase it; storage objects and rows are both gone, and the runner is safe to re-run after a crash between the two; the `evidence.erased` audit entry has counts and ids and no content (test greps the `detail` for any body, filename or address); `authenticated` and `service_role` cannot call the erase functions; `audit_log` rows themselves survive erasure.
- **Verified by:** time-travel tests against the local stack; a crash-injection test that aborts after storage deletion and re-runs.

## M8. Internal timeline page

One page, `/internal/matters/[id]/timeline`, anon key + the user's session, RLS only. Lists `matter_timeline`, shows consent state, dual-channel status, mono warnings, read receipts, and marks reads when an event is opened. Renders text only: no HTML email rendering, no inline attachments.

- **Done when:** a fee earner of firm A sees their matter's timeline; the same page for firm B's matter id returns not-found (test); a bundle of grep checks proves no service role symbol is in the client bundle; the page makes no write other than a read receipt.
- **Verified by:** Vitest for loaders; one Playwright test only if the read-receipt interaction needs a browser.

## Cross-cutting acceptance: the replay suite

`pnpm harness replay --scenario <name>` runs a scenario end to end on the local stack and prints the resulting timeline. Scenarios: `happy-call`, `declined-consent`, `mono-recording`, `duplicate-delivery`, `email-thread-out-of-order`, `hostile-email`, `retention-and-hold`. Running every scenario is the final acceptance check for the spine.

## Open questions (need an answer before the milestone that depends on them)

1. **Evidence bundle export** (M8+). The product description says "exportable evidence record" and the glossary lists "evidence bundle", but export is not in the in-scope list. Schema supports it (every artefact is hashed). Is a bundle exporter in scope, or deferred? I have not planned it.
2. **Consent mechanism** (M3). Announcement then continue (implied consent by staying on the line) or explicit keypress ("press 1")? Keypress is easier to defend; implied is better for callers. This decides whether `declined` and `no_response` exist at all.
3. **Retention period** (M7). No default is hard-coded. The COLP sets `retention_period_years` per firm; what value do you want as the seed in fixtures, and does any matter type (e.g. with indemnity insurance or a build-over agreement) need a longer period?
4. **Twilio-side copies** (M4/M7). After we verify and store a recording, Twilio still holds a copy. Deleting Twilio's copy is deletion. May the retention job do it on a schedule, or do you want Twilio's own retention setting to do it? I'd treat it as a retention-job step with its own audit entry.
5. **Storage tamper-evidence** (M2/M7). Postgres can make rows immutable even against the service role. Storage objects can be deleted by a leaked service role key. Options: (a) hashes in rows so loss is detectable (planned), (b) additionally a nightly job that re-hashes and records verification events. (b) is cheap; want it?
6. **Malware scanning of attachments** (M5). Not planned (no scanner in the stack). Attachments are stored inert and downloaded as attachments only. Is that acceptable for the spine?
7. **Edge Function vs Node for webhooks**: decided as Edge Functions (see CLAUDE.md), with the M3 spike as the checkpoint. Say so if you would rather host them in Next route handlers.
